⏺ Ingestion, parsing, chunking, extraction

  Ingestion
  - One command, docagent ingest <files or folders>. It skips unchanged files by
    content hash, replaces changed ones, and --force rebuilds.
  - All 3 reports are indexed: 94 chunks, 44 of text and 50 of figures.
  - Drawings are not ingested. They're processed when uploaded.

  Parsing
  - The PDF text layer is read directly with PyMuPDF. Headers, footers and blank
    pages are removed.
  - Each report's case details (report number, aircraft, location, date) are
    pulled from its first pages and prefixed to every chunk.
  - Section headings (A. Accident Information, D. Details…) are tracked and
    stored on each chunk.
  - Figures are found from their "Figure N." captions. The page region above
    each caption is cropped and saved as a PNG. Chart pages without captions are
    handled too.

  Chunking
  - Text is split by paragraph, up to 350 tokens per chunk, within one page and
    one section, so every chunk cites a single page.
  - Each figure chunk holds its caption, the labels printed on it, and the
    report sentences that cite it.

  Text extraction, OCR and VLM
  - No OCR anywhere in v1. The reports are born-digital, so the text layer
    covers them completely.
  - VLM (Qwen2.5-VL 7B, local):
    - describes figures at ingestion; used for search only, never as evidence
    - describes user photos
    - reads drawing tiles and names the feature each value belongs to

⏺ Evaluate it in layers, against hand-checked ground truth, so each part of the

  1. Ground truth

  - Hand-label 3–4 sheets chosen to cover the variety:

    - one dense FTC sheet, e.g. FTC-09 p1

  - Speed-up: pre-fill each sheet from the model's output, then correct it by
    looking at the sheet. Note the bias this creates: you may miss values the
    model also missed. To counter it, do one pass that scans the sheet
    independently for missing values.
  - Free partial ground truth: FTC-07's text layer gives the exact printed
    strings.
  - Worth checking: the drawings' notes reference NIST "Feature and
    Specification Index" files (..._fsi.pdf). NIST also publishes the CAD models
    with the annotations stored as structured data (STEP AP242). If those are
    downloadable, they're ready-made ground truth listing every annotation and
    its feature. Downloading them while building the eval set is fine; the
    system itself still never goes online.

  Label format, one file per sheet, e.g.
  eval/datasets/drawings/<drawing>_p<n>.json:
  {"features": ["F1: Ø20 side hole (left)", "F2: top face", ...],
   "values": [{"raw_text": "Ø20 +0.05 -0.10", "type": "diameter", "nominal": 20,
  "tol_plus": 0.05,
               "tol_minus": -0.10, "quantity": null, "datums": [],
  "characteristic": null,
               "feature": "F1", "bbox": [x0,y0,x1,y1]}]}

  "belongs to" scoreable.

  (after normalising) and both boxes are within 25 pt. In the outputs neither
  condition holds:
  - The same annotation is read differently in two tiles: Ø25 ±0.1 vs Ø25 ±0.15,
    Ø20 +0.05 vs Ø20 +0.05 -0.10, 2X Ø.250 +.003 vs Ø.250 +.003. The texts
    differ, so no match.
  - The boxes are imprecise. The same 60° ±0.5° landed at x=270 pt in one tile
    and x=361 pt in the other, so even identical texts fail the distance test.
  - Fragments aren't duplicates. Frame letters split out as datums (A, B, C) and
    stacked tolerances split in two (-.000) are different texts at different
    places. No dedup rule merges them; they're a reading problem.
  - Loosening it is risky. Real drawings repeat identical values (x.30 ±.02 four
    times on FTC-07), so "same text = duplicate" would delete real values.

  crops, so the same thing gets found several times, imprecisely located, and

❯ Quick qn - isn't our current proposed approach "overfitting" to these 11?        

⏺ Partly, yes. The idea generalises, but some of the specific rules are fitted
  to how NIST exported these 11 files.

  Fitted to these 11:
  - "Annotations are blue": a NIST styling choice. Other companies' drawings may
    use black for everything.
  - "Text is drawn as filled outlines": true for the PostScript exports, not for
    FTC-07 (real text), and not for many other CAD exporters.
  - "Frames are rotated quadrilaterals": how this exporter draws them; others
    draw separate lines.
  - The title-block regex (PMI … Test Case, nist_…): NIST-specific, as are the
    grouping distances, tuned by eye on 3 sheets.

  General:
  - Read the PDF's vector data first, use pixels only as a fallback.
  - One crop per annotation, so no duplicates by construction.
  - Choose GD&T symbols from a fixed list.
  - "Belongs to" via leader lines.
  - Check results against the text layer when one exists.

  How to keep it from overfitting:
  1. Pick the annotation layer automatically, not by hard-coding blue:
     - use the PDF's layer structure if it has one
     - otherwise the colour or line width whose paths look like text and lines
     - otherwise none, and go to step 3
  2. Accept text in either form: drawn outlines or the real text layer.
  3. Keep a fallback for anything without separable vectors (scans, photos,
     flattened PDFs): a text-detection model for boxes, then the same per-box
     reading.
  4. Make the title block generic: regex when it matches, otherwise the VLM
     reads the title-block region.
  5. Test on drawings it was never tuned on. This is the real check. Even a few
     drawings from a different source (another CAD tool, a scan) would show
     whether it generalises. Today it hasn't been tested on any.

  The QA side has the same issue: its fixes were tuned on the same 20 questions
  they're scored on.

  For the review call: the brief says over a million documents, "all very
  alike". If the client's drawings come from a consistent CAD export, exploiting
  that structure is a legitimate design choice, not just overfitting. But it
  has to be detected, not assumed, and backed by the fallback. I'd build the
  generic versions of 1–2 into step 1 (it costs little extra), and state 3–5
  explicitly in the write-up.

❯ Our system must work with JPGs too right (says image) so will these changes   
  generalize?                                                                   

⏺ Not by themselves. A JPG has no vector data: no paths, no colours as separate
  objects, no text layer, just pixels. So the geometry approach only applies to
  vector PDFs. JPGs, scans and photos of drawings need a different way to find
  the annotations.

  The fix is to split the pipeline in two:

              ┌─ vector PDF ─> annotation boxes from paths/text layer (exact)  
  ─┐
  input ──────┤                                                                 
  ├─> same back end:
              └─ JPG / scan ─> annotation boxes from pixels (detected)         
  ─┘   read each box (VLM),

     GD&T from fixed list,

     belongs-to via leaders,

     checks, JSON

  Pixel route for JPGs:
  - Text boxes: a small offline text-detection model. RapidOCR's detector
    installs with pip and runs locally on CPU. Use only its boxes, not its
    reading.
  - Frames: OpenCV rectangle and contour detection groups text boxes inside a
    frame into one annotation.
  - Leaders: OpenCV line detection, to find the line starting at each box.
  - Photos of drawings: correct the perspective and boost contrast first.

  The back end, where the VLM reads each crop and the rest follows, is
  identical, so most of the 7/10 work serves both routes.

  Expected quality:
  - Vector PDFs: best. Exact boxes, exact text where a text layer exists.
  - Clean JPG or scan: somewhat lower. Boxes are detected, not exact, but there
    are still no duplicates, since each box is read once.
  - Phone photo: lower again, and depends on resolution and angle.
  - Today's tile approach already accepts JPGs, and stays the last-resort
    fallback if detection finds nothing.

  A free test of the JPG route: render the 11 PDFs as JPGs and run them through
  the pixel route. The vector-route results are the reference, so we can measure
  how much quality JPG input loses without extra labelling. That's also a
  strong point for the review call.

⏺ I've set this up as one script, scripts/colab_experiment.py. It runs every
  check in order and saves each experiment to its own folder on Drive, so one
  Colab cell does everything. I tested it on the Mac (folder layout, manifest,
  summary); the GPU steps haven't run yet.

  What the script runs, in order (a failing step is recorded and the next one
  still runs):
  1. check: is vLLM up (starts it if not), GPU info, package versions
  2. ingest: indexes the reports; takes seconds if nothing changed
  3. bulk: all 11 drawings → one JSON each, with the new method. This is the
     deliverable.
  4. eval_pdf: scores those JSONs against the ground truth (CTC-01, FTC-07) and
     compares with the old-method baseline
  5. eval_jpg: feeds the ground-truth drawings as JPGs and scores the picture
     route
  6. qa: the 20-question QA eval, compared with the v3 result (checks the QA
     side didn't regress)

  What it saves. Each experiment is copied to Drive after every step, so a
  disconnect loses nothing:
  MyDrive/ColabProjects/experiments/<timestamp>_<name>/
    summary.md        headline metrics vs the baselines (start here)
    manifest.json     config, model, method, each step's status, duration and 
  outputs
    bulk/drawings/    the 11 drawing JSONs + bulk_summary.json
    eval/             all eval result JSONs (PDF, JPG, QA)
    logs/             full log of each step + vLLM log tail
  The model response cache is restored from and saved back to Drive, so
  re-running unchanged steps is quick.

  MyDrive/ColabProjects/. It needs to include the new

  with one change.
  - The diagnosis is confirmed from the output, not guessed: the same value
    13–15 times, always with the same box, from reads that hit the token limit.
  - Removing repeats within one read is safe. A legitimately repeated value
    (x.30 ±.02 four times on FTC-07) comes from different callouts with
    different boxes, so it's unaffected.
  - The cap needs care. Some over-merged callouts genuinely contain 6+ values,
    so a cap of 6 could drop real ones. I'd use ~10, applied after removing
    repeats.
  - I'd drop the repetition penalty I proposed. The model writes JSON, where
    field names and datum letters (A B C) repeat legitimately. A penalty could
    distort or break the output. Lowering the token limit stops loops more
    safely: real values come first, and a loop then stops after a few seconds
    instead of ~40.

  2. Single letters from FTC-07's text layer: medium-high confidence, real risk 
  if done carelessly.
