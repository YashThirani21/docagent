⏺ 1. Tracing, persistence and failure recovery

  Your Job-row idea is right. Use SQLite for it, and treat logs as a secondary 
  record. SQLite needs no extra service, keeps the data in-house, and runs in
  WAL mode so the bulk threads can write at once. The same schema moves to
  Postgres at scale. Use three tables:

  table: requests
  one row per: user request
  key fields: id, batch_id, status (queued/running/succeeded/partial/failed),
  text, created/started/ended_at, agent versions + config hash + git sha, token
   totals, LLM call count, cache hits, error
  how it's written: updated at each change of state
  ────────────────────────────────────────
  table: tasks
  one row per: attachment, which is the unit you retry
  key fields: request_id, path, sha256, route, tier, confidence, reason, status,

  stage, attempts, output_path, error and traceback, heartbeat_at
  how it's written: updated at each stage boundary
  ────────────────────────────────────────
  table: spans
  one row per: step
  key fields: span_id, parent_id, request_id, task_id, name (router.rules,
  router.vlm, drawing.find_annotations, drawing.read_callout, qa.retrieve,
  qa.generate, llm.call), start, end, status, attrs JSON
  how it's written: row added when the step opens, closed when it ends

  - Write on every event, not on a timer. Each change of state is a tiny
    transaction, so a crash loses at most the step that was running. A span row
    added at open time means a crash leaves a visible running span that shows
    where it died.
  - Record tokens and timing in one place. VLM._complete (src/docagent/llm.py)
    already logs time, tokens, image count and finish reason. Send the same
    values to the current span, plus cache_hit, the model, and the prompt hash,
    which is also the cache filename. That filename is your link to the full
    prompt and raw reply, so you don't store prompts twice.
  - Store usage in the VLM cache. Save {text, usage, latency} as JSON instead of
    plain text. Otherwise every cached re-run, which is most eval runs, reports
    0 tokens and 0 s, and your cost and latency numbers are wrong.
  - Pass the current request and span through contextvars. Gotcha:
    ThreadPoolExecutor does not copy contextvars to worker threads. Wrap
    submissions with contextvars.copy_context().run, both in bulk and in the
    parallel drawing reads, or spans lose their parent.
  - Logging: keep Python logging for the human-readable story. Add a
    logging.Filter that stamps request_id/task_id from the contextvar and writes
    JSON lines to a file. Don't parse logs for metrics. SQL is the source of
    truth; logs are for debugging.
  - Make lookups easy: add docagent trace <request_id> to print the span tree
    with durations and tokens, and docagent requests --status failed --since 1h.
    For a free UI in the demo, run datasette store/traces.db. It works offline
    and lets the reviewer browse and filter rows.
  - Why not Opik or Langfuse: the cloud versions break the privacy rule.
    Self-hosting them means several containers for something you can write in
    about 150 lines and explain line by line. Name them as the production option
    in your design page.

  Failure recovery:
  - Within a task, it mostly works already. The temperature-0 VLM cache acts as
    a checkpoint: a re-run after a crash replays the finished calls for free
    (your fix2 run took 7 minutes because of it). Say this in the review; don't
    build per-stage checkpoints.
  - Across tasks: mark a task succeeded only after its output is written
    atomically (write to a temp file, then os.replace). On startup, mark running
    tasks with a stale heartbeat as interrupted and re-queue them.
  - Retries: retry transient errors (connection refused, timeouts from vLLM or
    Ollama) with backoff; the openai client's max_retries covers this. Don't
    retry deterministic failures like parse errors. Record them and move on.
  - Idempotency key: sha256 + extractor version + config hash. If a succeeded
    output already exists, skip the file. With a million near-identical files,
    this also removes exact duplicates.

❯ Based on the current system, retrying an unsuccessful request only creates a  
  new fresh request having lost the intermediate progress right? Is that        
  fixable?                                                                      

⏺ Partly. A retry does create a new request with a new id, but most of the
  expensive work isn't lost.

  What survives: the model response cache. Every model call that finished
  normally is saved to disk, keyed by a hash of the model, prompt and images.
  With temperature 0, the retry sends exactly the same calls, so the finished
  ones are replayed for free. Only the call that failed, and any calls that
  never ran, go to the model again. The non-model steps (rendering, vector
  geometry, OCR, symbol classification) run again, but they take seconds next to
  minutes of model time. This was tested: the cached re-run of CTC-01 made 0
  calls to the model.

  The cache doesn't help in four cases:
  - a reply that was cut off at the token limit is never cached, so it runs
    again;
  - the cache only works at temperature 0;
  - a prompt containing anything that changes between runs, such as a timestamp
    or request id, would miss every time. I haven't checked the prompts for
    this;
  - after a config or prompt change you're running a new version, and missing
    the cache is correct.

  What is lost:
  1. The link between attempts. The new request has no connection to the failed
     one, so the history reads as two unrelated requests.
  2. Which attachments already succeeded. A retry re-processes every attachment,
     including the ones that worked. Thanks to the cache that costs little, but
     the old outputs aren't reused and the user gets a fresh response for
     everything.
  3. Steps that don't call the model. Loading the index and running OCR repeat.
     That's minor.

  Yes, it's fixable, and it's mostly the same machinery as bulk resume:
  - docagent retry <request_id> creates a new request with a retry_of link and
    an attempt number. Each attempt stays its own trace instead of being written
    over, so you can see why attempt 1 failed and how attempt 2 went.
  - Reuse finished attachments: an attachment that succeeded and whose output
    file exists is copied into the new request as reused. Only failed or
    interrupted attachments run again, and their finished model calls still come
    from the cache. This needs each attachment's output path saved and output
    files written atomically. Both are already on the bulk list.
  - Batch resume is the same thing for every request in a batch that isn't
    succeeded: bulk --resume <batch_id>.
  - No extra step-by-step checkpoints. The cache already covers the expensive
    part. Saving the results of each pipeline stage would add complexity to save
    seconds.

  I'd build retry and bulk resume together as the next step, along with the
  --file lookup.

  What is durable now (CLI bulk)
  - The batch is saved before any work starts. Every file is recorded as queued,
    so after a crash you can tell finished, interrupted and never-started files
    apart.
  - A file counts as done only once its output is complete. Outputs are written
    in a single step, so a half-written file is never treated as done.
  - A crashed process is noticed straight away (from its process id and host).
    Its requests become interrupted and can be resumed.
  - --resume re-runs only unfinished files, and inside each one, finished model
    calls come back from the cache.
  - A repeated run skips finished files, and a bad file fails on its own without
    stopping the others.

  Remaining gaps, most important first
  1. Uploaded files aren't kept. The database stores paths. Paths in data/ are
     fine, but the chat's uploads sit in Gradio's temporary folder, which isn't
     permanent storage. Once those files are cleared, retry and --resume stop
     with "file missing". The fix is small: when a request is submitted, copy
     each file into store/uploads/<sha256> and record that path. Identical
     uploads also get stored once.
  2. Chat uploads run inside the browser request. If the tab closes, the
     connection drops or the app restarts mid-batch, the work stops. The user
     never got a batch id, so the only way to recover is the CLI. Streaming
     progress alone doesn't fix that, because it still runs inside the same
     request. The robust shape:
     - the chat submits the batch and shows its id straight away;
     - a background thread in the app works through it;
     - the chat streams progress by reading the batch's status from the
       database.

     Reloading the page then loses nothing, and the app can pick up unfinished
     batches when it restarts.
  3. The embedded vector store allows one process at a time. Running bulk while
     the chat app is open fails as soon as a file needs the report index (photos
     or report pages). Drawing-only batches are fine. The fix is the Qdrant
     server, which is already in the Docker plan. Until then, say this in
     USAGE.md.
  4. Missing conveniences:
     - No zip upload; bulk takes folders only.
     - No batch summary with counts (you can only list a batch's requests).
     - No download of all of a batch's results.

     All small, and the summary and download are useful in a demo.
  5. No protection against two workers picking up the same file. Two processes
     resuming one batch at once could both process a file. On one machine, the
     process-id check mostly prevents this. At scale, a worker would mark a file
     as taken in the database before starting on it (Postgres SELECT … FOR
